# Windows/OS control: windows, media, apps, files

## Purpose
Windows control: windows, media/volume, apps, clipboard, sticky notes, files, Spotify, YouTube, Copilot.

## Key pieces
- **Window layout:** chat.py `_semantic_window_adjust` (verbs + position words + percentages, spoken numbers → digits) → `window_layout.adjust_active_window(position, width_percent, height_percent, app_name)`. `win32_find_window` does fuzzy title/process matching and skips the Jarvis overlay. Close/min/max/snap go through `win32_*` helpers.
- **Files:** `file_ops`: `_resolve_path` shortcuts (Desktop/Downloads/Documents…; bare names → Desktop), read txt/pdf/docx (long files LLM-summarised), write/append/list/move, delete → Recycle Bin (send2trash), search, bulk_rename, diff.
- **Spotify cold start:** if Spotify wasn't running, wait for its UI (≥15 buttons), then send the search link again (the Store app opens Home and drops it). The link is also re-sent once if the results don't match after 5 s. The window is found via EnumWindows (largest visible spotify.exe window) + `uia_local`.
- **Spotify** (`spotify_service.py`): `play_music(song)` → `play_song_dynamic`: `start spotify:search:<q>` → wait for fresh results (diff of visible "Play …" buttons) → invoke the Top Result card's unnamed **"Play"** button via pywinauto UIA (else best fuzzy "Play <title>" row) → confirm via window title, which becomes "Artist - Song" while playing (idle = "Spotify Free/Premium"). "X by Y" is searched as "X Y". Pixel search for the green button is only a last-resort fallback. Before pressing, `_page_matches` requires ≥60% of the query's words on the visible buttons/links (Spotify keeps showing the previous page for a moment; pressing too early played "Jai Ho" for "shape of you"). After pressing, `_title_match` checks the window title. It switches to a song row only if a row matches clearly better (≥0.6), so artist/playlist requests ("play arijit singh") are accepted as they are. `spotify_control(action)` presses the player-bar buttons (Previous / Play|Pause / Next / shuffle / repeat / like) found in the bottom 110 px, or reads the title for `now_playing`. `open` = `start spotify:`. `close` = WM_CLOSE to its windows, then `taskkill /IM Spotify.exe /F` if it only hid to the tray. With no Spotify window, play/pause/next fall back to media keys. Blocking ~3–10 s.
- **YouTube** (`youtube_control.py`): `_fetch_results` parses `ytInitialData` from the results page → `[{id,title,channel,duration,seconds}]`. `youtube_search` opens the results (or, with autoplay, `watch?v=<id>` of #1) and replies with the top 5 numbered. `youtube_play_result(choice)` first **reads the videos on screen** (`youtube_player.page_videos`: rendered `ytd-video-renderer`/`ytd-rich-item-renderer`/`yt-lockup-view-model`… in visual order, skipping ads, Shorts shelves and hidden cached pages). So "the first result" is the first one the user sees, in YouTube's personalised order; on a watch page a Jarvis list younger than 30 min wins, else the up-next sidebar. The saved list is only a fallback, and it is ignored when older than 30 min. It then resolves ordinals/numbers/"last"/"next"/"latest"/"most viewed", "the N minute one" (closest duration), "by <channel>", or a fuzzy title, and opens it with an in-page click (`open_video`) or the URL; "it/that" with a video already open → resume. Navigation reuses the YouTube tab (Ctrl+L, paste URL, Enter; clipboard restored), else `webbrowser.open`. `youtube_control(action, amount, value)` handles close/exit-mode/back-to-results and next/previous *search result*, and passes everything else to `youtube_player.player_action`. **Channels:** `youtube_channel(name, play_latest)` finds the channel via the "Channels" search filter (`_find_channel`: tries twice, then plain results, keeps only a name match ≥ 0.5), opens `/@handle/videos` and loads its videos (newer `lockupViewModel` format, parsed by `_parse_videos`, which also handles `videoRenderer`). "latest/newest" → #1, "most viewed/popular" → by views, "oldest" → last. name `__current__` ("open his channel") = channel of the playing video. **Replies are deliberately short** ("Here are the results for X, Sir. Which one should I play?"): the voice agent drops speech that overlaps Jarvis talking, so reading titles made it "not listen". The list is read only on request (`youtube_list_results`: "read the results", "what are the options").
- **Switching videos:** `navigate()` reuses the YouTube tab via the script bridge (`setTimeout(location.assign, 700)`, so the result marker is read before the page unloads). A timeout followed by a title change counts as success. Only then does it fall back to the address-bar paste, and before any new tab it pauses the old video (`pause_quietly`), so two videos never play at once. It returns `…-muted` when YouTube's saved mute flag is on, so callers wait 2.5 s to unmute only then. "Next video": a channel list → next item; otherwise YouTube's Up Next (the player's Next-button href, then the first sidebar video, then `nextVideo()`, which only works inside playlists). Success is checked by a title change and never claimed without one.
- **Title-marker restore** only puts the old title back if the page did not navigate (it used to overwrite YouTube's new title with the previous video's). In-page navigations (next, back, `open_video` click) are delayed 600 ms so the marker is read first.
- **Fullscreen** (verified live 3/3 runs: fullscreen → pause/resume/forward/speed 2x/status/rewind/normal speed/next/pause, all staying fullscreen → exit):
  - Entering: YouTube's fullscreen button via the page script, then the `f` key; the result is verified (window covers the monitor) and never claimed otherwise.
  - Inside fullscreen, these use YouTube keys (no leaving it): forward/rewind (`l`/`j` ×10 s + arrows ×5 s), 10%-steps (digits), restart (`0`), next (`Shift+N`), faster/slower, captions toggle; pause/play use the media session. Exact commands (speed 1.75x, go to 5:30, status, volume) leave with Esc, run the script, and come back with ONE verified `f` keypress (a script click plus a fallback key raced and toggled it back off).
  - **Never press Esc for focus in fullscreen** (it exits it): `_focus_page` uses UI Automation (`_uia_focus(hwnd, "document")`) and gives up rather than pressing Esc.
  - Browser fullscreen (F11) is told apart: still covering the monitor after Esc → don't restore anything.
- **Focus** (`focus`, `_uia_focus`): on freshly opened windows Edge's keyboard focus can sit on an internal container ("View" pane), where Ctrl+L / F6 do nothing. Address bar and page focus are set directly through UI Automation (`SetFocus` on the `OmniboxViewViews` Edit / the Document), with Ctrl+L / F6 as fallback. `focus()` retries with an Alt tap (lets SetForegroundWindow through the foreground lock) and a TOPMOST toggle. `_page_focused` now requires a Document ancestor (browser toolbar buttons don't count).
- **Audible playback:** starting a video unmutes the player (YouTube stores a "muted" flag in localStorage; this user's was set, so picked videos played silently). `open_video` sets unmute timers that survive the in-page navigation; full page loads call `ensure_audible(delay=2.5)`. Volume is only raised if it is ~0.
- **Player control** (`youtube_player.py`, helper, not a registered tool): runs a one-line script in the page through the address bar and uses YouTube's own player API (`#movie_player`: seekTo, setPlaybackRate, getVideoData, setVolume…). Flow in `run_js`: focus the browser window → leave HTML fullscreen if the window covers the monitor (Esc) → Ctrl+L until UIA says an Edit has focus (`_focus_address_bar`) → put the script on the clipboard (verified) → Ctrl+A, type `javascript:` (browsers strip it on paste) → paste → **poll the address bar's value (UIA ValuePattern, up to 1.2 s) until it equals our script**, else abort → Enter. Abort = `_focus_page` (Esc, Esc, F6 until focus is no longer the address bar/tab strip) and return `noaddressbar`; `_js` retries once because nothing ran. The script writes `__JV<nonce>__{json}__JE__` into `document.title` and restores it 1.5 s later; Python reads it with `GetWindowTextW`. The next call cancels that timer (`window.__jvT`) and reuses the saved title (`window.__jvO`). If we left fullscreen, the script clicks the fullscreen button again. ~1 s per command.
  Actions: status (title/channel/position/time left/speed/volume/ad), pause/play (exact, reports "already paused"; a pause while the video is still loading, i.e. player state -1/3/5, also pauses it once it starts), forward/rewind N s, seek_to (clock or duration), seek_pct, seek_end, restart, speed (exact 0.1–16x; ≤2x via the player API, >2x on the `<video>` element), faster/slower (±0.25), volume/volume_up/down, mute/unmute, captions on/off/toggle, loop, quality (best effort), chapters: list/current/next (`skip_part`, falls back to +30 s with no chapters)/previous/goto by number or name (from `ytd-macro-markers-list-item-renderer`: `[id=time]` + `h3`), skip_ad, like/dislike/unlike/subscribe (checks sign-in via `[id=avatar-btn]`), theater, miniplayer, pip, fullscreen/exit, next/previous video.
  `parse_player_command(text)` → (action, amount, value): spoken numbers and durations ("10 minutes", "1 hour 5 min", "half a minute"), clocks ("5:30", "1:02:03", "go to 5 30"), "2x"/"1.5 times"/"double speed"/"normal speed", "the 3 minute mark", "halfway", "75 percent", "skip this part / the intro", "go to chapter 3 / the <name> chapter".
  Keyboard fallback (`_fallback`): **Firefox only** (it blocks `javascript:` in the URL bar). In Edge/Chrome a failed script replies "please say that again" and presses nothing. `send_keys` calls `_focus_page` before any single-key shortcut. YouTube shortcuts (k, l/j×n, digits, Shift+,/. for speed, m, c, f, t, i, Ctrl+←/→ chapters). Status, volume %, loop, quality, like, etc. need Edge/Chrome.
- **YouTube mode** (the "open YouTube, then wait for me" flow): state lives in `app/memory/youtube_session.json` (`active`, `step` await_query/results/playing, `query`, `results`, `current`, `updated`); active for 20 min after the last YouTube command. In `chat_endpoint`, right after the WhatsApp flow intercepts, `parse_youtube_followup(prompt)` maps follow-ups (player commands first via `parse_player_command`, then search/pick): "lofi beats" (plain text, only right after "open youtube" and only if `keyword_detect_tool` finds nothing else), "type/search X", "play the second one", "3", "the one by X", "play X" (not in results → YouTube autoplay search), pause/resume/full screen/mute/captions/speed, "skip 30 seconds", "go back 10 seconds", "next/previous video", "back to results", "close youtube", "exit youtube mode". Anything unrecognised (or mentioning spotify/whatsapp) falls through to normal routing. **Mode expired but a YouTube tab in front** (`youtube_tab_open()`): `parse_youtube_followup(prompt, controls_only=True)` still takes unambiguous player commands ("speed 2x", "forward 10 minutes", "go to 5:30", "skip this part"). Words that also fit Spotify/the OS (`_AMBIGUOUS`: pause, play, mute, status, like…) need "video"/"youtube" in the sentence.
- **chat.py wiring:** media tools (`_DIRECT_MEDIA_TOOLS`) run via `_run_direct_tool` → `asyncio.to_thread`, and the tool's string is the reply (no LLM rephrase, and the event loop isn't blocked). If the LLM router picks `open_website("youtube")`, it's turned into `youtube_open`. Keyword order in `keyword_detect_tool`: Spotify queries (now playing / like / shuffle) → "play X on youtube" → "play X on spotify" → reference plays ("play that video", "open the third one") → `youtube_play_result` → "pause the music" → `spotify_control`, bare "pause" → media key → bare "play X" → Spotify → YouTube search → "open youtube" → `youtube_open`. "next/previous song" → `spotify_control`.
- **Stopping whatever is playing** (`media_sessions.py`, helper; tool `media_control(action, app)`): uses Windows' media sessions (System Media Transport Controls via `winrt-Windows.Media.Control`), the same list the volume flyout shows. Every app/tab with media has one: Spotify, each browser tab with audio (also background tabs), VLC… "stop/pause (the song/music/it)", "close this song", "resume", "next/previous song", "what's playing" all route to `media_control`. So songs Jarvis didn't start, background tabs and media from before a restart are all covered. The **reported status lags ~2 s in Edge**, so it never decides whether to act: pause asks every matching session (idempotent), play resumes the best candidate (title match > last player > Windows' current session); the status only words the reply. `media_sessions` imports `onnxruntime` before `winrt` (the other order breaks onnxruntime's DLL init: "DLL initialization routine failed"). A YouTube tab's own pause/play uses its media session (matched by video title) only in fullscreen or when Edge isn't in front; otherwise the exact page script.
- **Which player gets "pause it"** (`media_state.py`, helper): `spotify_service` / `youtube_control` record the last app used in `app/memory/media_state.json`. `chat._media_target()`: named app ("spotify", "video/youtube") > last app if still open > whichever is open > OS media key. It covers pause/resume ("pause", "pause it", "pause that song", "stop the music", "resume", "play it again") and next/previous song. In YouTube mode, a bare pause/play/mute defers to the router when the last app was Spotify.
- **Multi-step media commands** (`chat._media_compound`, runs before the YouTube-mode intercept): splits on and/then/after that, and runs only if EVERY clause is a media command, so "play rock and roll" stays one song. Platform per clause = its own explicit words (youtube/video/watch/channel vs spotify; song/music are neutral) > the previous clause's platform > a platform named anywhere in the sentence (`_to_platform` re-targets pause/play/next/previous and play X). "close this video and play X" becomes pause + play in the same tab; "close youtube and play X" → X on Spotify; "open youtube and play X" drops the redundant open. Replies are joined, with pure acknowledgements dropped (`_run_direct_tools`).
- **Switch / close / another** (keyword router + YouTube-mode parser): "switch to X", "change it to X", "put on X", "play X instead" → play X. "close/stop this song" → pause the active player. "close this video" → close the YouTube tab. "play another song/video", "something else", "next one" → next on the active player. "go back (to the previous video)" → browser back. "play X video" / "watch X" → YouTube. A bare "play X" goes to YouTube when YouTube was the last player (unless it says spotify, or "the song X" / "X song").
- **One media thread** (`chat._MEDIA_EXECUTOR`, 1 worker): all media tools run on it, so UI Automation stays on one thread and two commands never type at once. **`uia_local.py`** gives each thread its own UIAutomation object. pywinauto's shared `IUIA` singleton belongs to the thread that created it (in the backend that can be the screen watcher), and calls from worker threads came back empty: "already paused" / "couldn't reach the player controls" right after a song started. Spotify and the YouTube address-bar checks use `uia_local` now (also faster: Spotify pause 0.3 s).
- **Media fast path** (`chat_endpoint`, before task-resume detection): if `keyword_detect_tool` returns a media tool, it runs immediately. Otherwise "resume the music" was caught by the *task*-resume detector (LLM + screen vision, 18 s, did nothing).
- `keyword_detect_tool` strips a leading "jarvis," and trailing punctuation first (voice transcripts arrive as "Pause that song.").
- **Volume:** volume/media keys via pyautogui.
- **Misc tools.py:** `open_app` (known-app map), sticky notes (tkinter thread), `set_reminder`, `calculate`, clipboard, `type_text`, `create_word_doc`, `read_pdf_text`, Copilot (`open_windows_copilot`, `send_to_copilot`), `take_screenshot`, `lock_screen`, `get_system_info`.

## Gotchas
- `pyautogui.FAILSAFE = False` in tools.py.
- Everything is Windows-only (win32 APIs); it can't run headless.
- Spotify and Chromium build their UIA tree lazily: the first query after launch returns ~4 buttons. `_buttons()` retries. pywinauto needs COM in the calling thread, so `spotify_service._com_init()` runs first (tools run in worker threads).
- "play X" means Spotify, except in YouTube mode, where it plays on YouTube. "play X on spotify" always goes to Spotify.
- YouTube result numbers follow Jarvis's spoken list, not the personalised on-screen order, and player control needs the YouTube tab to be the active tab of a browser window. See KNOWN_ISSUES.
- `run_js` scripts are URLs: no raw `%` or `#` (use `[id=x]` selectors; user strings go through `_js_str`). Every statement needs `;` (the address bar drops newlines).
- Title-marker timing was measured: a 150 ms marker was missed 6/6 times, 550 ms 1/8, 1.5 s with timer-cancel 10/10. Don't shorten it.
- Desktop automation shares the keyboard and clipboard with the user. The address-bar value check exists because a failed paste once sent "javascript:" to Bing and navigated away from the video. Before the value was polled (a single read 80 ms after paste), Edge hadn't finished filling the box. The check aborted, and the old keyboard fallback then typed Shift+,/Shift+. into the address bar ("<<<<<<<<>>>>>>>"): 2026-09-30 user report, fixed.
- Failures log one line to the backend console: `[youtube_player] address bar never got focus…`, `script not in address bar…`, `no result marker…`, `[youtube_control] no channel found…`, `follow-up parse error…`.
- `_is_positional()`: "the first result", "number 3", "the latest one" always go to `youtube_play_result` (which reads the screen), even with no saved list. Before, they could become a search for the words "the first result".
- In `parse_youtube_followup`, the local `intent(tool, **args)` helper must not name its first parameter `name` (it collided with `youtube_channel(name=…)` and silently broke those intents).
- Spotify Free: only the Top Result is pressed. For an artist/playlist query that plays the artist/playlist, which is intended.
