# Known issues

Originally found in the code survey of 2026-09-28 (commit cb8a3aa). Most were fixed the same day. Delete an entry once it's fixed, and add new ones with evidence plus file/line.

## Open
- **Exact resume replica — remaining limits (2026-10-03).** (1) Fonts on very low-res references (< ~60 dpi) can land on a look-alike family/weight; a paid font is only exact if its file is in `data/fonts/user/`. (2) A horizontal contact strip is rendered as a vertical list; free-form layouts (e.g. tabs scattered over a diagonal split, `Screenshot_2026-10-03_011131_*`) keep their background exactly but sections flow in columns. (3) One colour per OCR line (two-colour lines blend). (4) Viewer overlays inside the page (Google Lens button, "storage.googleapis.com" pill) can stay in the plate when they span columns. (5) A colour request in chat doesn't recolour an exact copy (use the editor's 🖌 Colours mode). A gradient or photo-like texture in the reference's background is recoloured only where it is close to the picked colour. Evaluate with `scripts/replica_eval.py`.
- **Resume editor undo — limits (2026-10-04).** The editor's Ctrl+Z history belongs to one editor session: a resume change made through Jarvis chat (or a new resume) changes `_state_rev`, so older steps are dropped on the next editor load. Structural steps older than the last 40 server snapshots (`app/memory/resume_undo.json`) report "too old to undo". A free image deleted and then restored after an editor reload shows grey until the next reload (its picture is reloaded from `path`). Typing inside a free text box (double-click) uses the browser's own undo until you click away; then the whole edit is one step.
- **Colour mode limits (2026-10-04).** A swap matches a colour within a small tolerance, so two different-but-close shades swap together. On an exact copy the contrast guard may switch text to a readable palette colour after a dark/light background swap (pick the text to set it yourself). Designs changed before 2026-10-04 may still carry shapes/styles from another template (they were shared then); delete them once, and from now on each template keeps its own.
- **Free-form copies on photographed/JPEG references (2026-10-04).** The shading of a large dark area can still be taken as a heading box, chips or rating dots, e.g. the dark-green column of `Screenshot_2026-10-04_121617_*`. A section placed there can then get a dark patch behind its heading or list. Planned fix: a contrast check (a decoration must differ visibly from its surroundings). Campus-format detection needs an education table header row. Campus resumes made before 2026-10-04 keep their old exact-copy design until they're created again from the image.
- **Resume vision quota.** `qwen/qwen3.8-27b` on Groq has a 200k tokens/**day** cap; one resume image costs two vision calls. `resume_builder` falls back to Gemini (`gemini-flash-lite-latest` worked 2026-10-02; `gemini-2.0/2.5-flash` return 404 for this key) and caches each design by image hash.
- **Module-global conversation state (not changing, by design).** `llm.conversation_history` and the `api_*_flow` dicts in `app/api/chat.py` are shared by every client (UI, voice agent, overlay). For a single-user assistant this is deliberate: the voice agent and the UI see the same conversation. Only revisit if Jarvis ever serves several users; that would need a session id in `ChatRequest` threaded through chat.py and llm.py.
- **Gmail API token revoked.** `token.json` fails refresh with `invalid_grant`, so email tools fall back to opening Gmail in the browser. To restore the API path: delete `token.json`, run `python -c "from app.services.gmail_tool import _get_gmail_service; _get_gmail_service()"` and approve in the browser. `calendar_token.json` may need the same treatment via `calendar_tool._get_calendar_service`.
- **Postgres/pgvector knowledge DB unreachable.** The `DATABASE_URL` Supabase host no longer resolves. `/memory/ingest` now falls back to MySQL+FAISS memory. The "what/how" knowledge RAG in chat.py returns nothing (harmless, since `llm.py` recalls from MySQL anyway). Either point `DATABASE_URL` at a live pgvector DB or remove it.
- **Groq free-tier token limit is the real throughput cap.** Measured 2026-09-28: `openai/gpt-oss-20b` allows **8,000 tokens/min**. `TOOL_ROUTER_PROMPT` is ~2,450 tokens (was ~1,930 before fix #5 added 36 tools), and the chat reply (system prompt + memory + history) draws on the same bucket. So a few non-keyword messages per minute trigger 429s. The SDK then retries silently (a slow reply), or the router returns None (treated as "no tool"). Options: upgrade the Groq tier; route with a different model that has its own bucket; or trim rarely used tools from the router prompt (keyword routes still cover them).
- ~~YouTube result numbers follow Jarvis's list, not the screen.~~ Fixed 2026-09-30: picks read the page (`youtube_player.page_videos`). The note below is kept for the fallback path (no YouTube tab in front).
- **YouTube result numbers follow Jarvis's list, not the screen (fallback only).** `youtube_control._fetch_results` scrapes an anonymous results page; signed-in YouTube reorders results (and adds Shorts shelves), so "the second one" means #2 in the list Jarvis read out. Naming a title or channel ("the one by Lofi Girl") always works. Reading the on-screen order isn't possible: Chrome/Edge don't expose page content to UI Automation without `--force-renderer-accessibility` (checked 2026-09-28).
- **YouTube player control needs the YouTube tab in front.** `youtube_player.youtube_windows()` only sees each browser window's *active* tab (window title). If the user switches tabs, commands reply "I don't see a YouTube tab in front".
- **Other desktop automation running at the same time breaks YouTube control.** Anything that steals the foreground or types while `run_js` works (the user typing, or another agent driving Edge, as seen 2026-09-30) makes the command abort ("please say that again") or retry. It no longer types into the wrong place.
- **YouTube player control briefly takes over keyboard, clipboard and tab title (~1 s).** `youtube_player.run_js` types into the address bar, so if the user types or copies at that same moment the command can fail. The address-bar value check makes it abort (Esc) instead of submitting garbage. The tab title shows `__JV…` for 1.5 s. Typed `javascript:` entries may show up in the browser's address-bar suggestions. Firefox blocks this path, so it gets keyboard shortcuts only (no status, exact volume, loop, quality or likes).
- **YouTube quality change is best effort.** `setPlaybackQualityRange` is deprecated in YouTube's player, which may ignore it; the reply says so.

- **Groq free tier caps how much Jarvis can talk: each gpt-oss model has 8k tokens/min and 200k tokens/day.** One non-keyword request costs ~4k tokens (router prompt ~2.8k + reply), so both models together give ~4 requests/min and roughly 100 requests/day. When both are exhausted the voice agent says "I've hit my AI usage limit". Fixes: Groq Dev tier, or shrink `TOOL_ROUTER_PROMPT` (the biggest cost). Also "what time is it?" gets "I don't have real-time access" from the LLM (routing gap).
- **Voice: no acoustic echo cancellation.** On laptop speakers the mic hears Jarvis. The double-talk detector (echo gain learned from playback level) plus `Speaker.is_echo` handle it, but a barge-in is transcribed from mixed audio. Headphones make it perfect. The detector was tuned on synthetic audio, not in a real room yet.
- **Voice: Groq STT quota is 2,000 requests/day** (`x-ratelimit-remaining-requests`). Every VAD utterance while idle costs one request. Below 150 remaining, or after a 429, idle-room speech goes to local Whisper first (slower, ~1.7 s, weaker Hindi). `JARVIS_STT_MODE=local` never uses Groq.
- **Screen watcher exhausts the vision model's daily quota.** `screen_vision` background watcher calls `qwen/qwen3.8-27b` every 15 s; on 2026-10-01 it hit the 200k tokens/day limit, after which every screen read failed slowly. Consider a longer interval or disabling the watcher.
- **Voice: offline TTS has no Hindi voice.** If edge-tts is unreachable, Windows SAPI (Hazel, en-GB) reads Hinglish with English phonetics.

- **PPT: designing a rich pasted deck takes ~1–2.5 min.** `architect_slides` makes one Groq 120b call per 2 slides plus a retry per slide that dropped content (6 dense SIH slides measured 47–156 s). Vision captions/theme reading share the 200k-tokens/day `GROQ_VISION_MODEL` quota; when it is exhausted placement falls back to keywords and the theme to the local PIL palette (no failure).
- **PPT: very long slides still end up small.** Composite slides pick the largest font that fits (floor 8.5 pt). A slide with ~300 words, like the KarmaSkill "Impacts and Benefits", renders at about 8.5–10 pt; splitting it is left to the user ("split slide 5 into two").

- **PPT: Groq daily token caps bound how many AI-written decks fit in a day.** gpt-oss-120b and 20b each allow 200k tokens/day (plus 8k/min). A grounded 20-slide deck needs roughly 35–60k tokens; testing on 2026-10-01 exhausted both. `_llm_json` then falls back to Gemini (`gemini-3.8-flash` is often 503 "high demand", `3.5-flash-lite` works). Research itself uses no LLM tokens.
- **PPT research depends on `ddgs` web search, which throttles bursts.** Searches run ≤ 2 at a time with backoff; if it still returns nothing, Wikipedia alone grounds the deck (fewer facts → more qualitative slides).
